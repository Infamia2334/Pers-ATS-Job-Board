# AGENTS.md

Personal job-discovery engine: scrapes public Ashby / Greenhouse / Lever job-posting JSON APIs plus six no-auth non-ATS feeds, and writes `Live_Openings_Feed.csv`. Core scraper is stdlib-only, Python 3.12+ (no install step needed for scraping); the *optional* AI enrichment layer needs `pip install -r requirements.txt` (google-genai) and is off without it. Code is a package split by responsibility — `jobsearcher/config.py` (TOML loading + compiled filter regexes, the only place `CFG`, `WEB_PORT`, etc. live), `fetch.py` (gzip-aware `fetch_json`/`fetch_text`), `sources.py` (one `check_*` per board/feed plus `_row` normalization and `_zoho_site_entries`; `_row`'s optional `desc` param attaches an internal `_desc` key for enrich), `engine.py` (`collect_jobs(prev_jobs=...)`, dedup, enrichment orchestration, strips `_desc` before rows escape), `enrich.py` (optional Gemini Flash-Lite annotation — see `[enrich]`), `page.py` (UI HTML, placeholders `__HEADLINE__`/`__PROFILE_SUMMARY__`), `web.py` (`run_web`), `cli.py` (`main` CSV mode, `verify_boards`, `_probe_source_liveness`). `discover_jobs.py` at the repo root is a thin launcher dispatching `--web` / `--verify` / plain CSV mode; it re-exports `WEB_PORT` etc. so `python3 -c "import discover_jobs as d; print(d.WEB_PORT)"` keeps working. Three modes: `./start.sh` (or `python3 discover_jobs.py --web`) serves a clickable UI at `http://localhost:<config [run].web_port>` (scrapes in the background at startup; result clicks serve a ≤10-min cache instantly); `python3 discover_jobs.py` runs CSV mode and prints a top-20 preview (one row per company, alphabetical sorting would otherwise fill it with the first company's rows); `python3 discover_jobs.py --verify` checks every board slug for liveness (404 = dead, 0 postings = empty; one retry on timeout — transient under 40-way concurrency), then runs `_probe_source_liveness()` over the non-ATS feeds, and prints ok/empty/dead per slug plus a summary. Run `--verify` after any board-list change: wrong slugs fail silently everywhere else.

## Config (config.toml — the single source of truth)

Everything tunable lives in `config.toml` next to the script; override the path with `JOB_CONFIG`. Nothing about what the scraper targets is hardcoded anymore — code changes are only needed for a new *source type*. In-code `DEFAULTS` mirror the file so a trimmed config still behaves, but edits belong in the TOML.

- `[profile]` — the feed's owner layer: UI headline, `years_experience` (the YOE cap), `resume_pdf` (master resume for the `Recommended_PDF` column). NOTE: the published config keeps personal identity (real name, headline specifics, summary, resume version) OUT — treat this repo as public and keep such values only in your local copy; if you must personalize locally, expect `git diff` noise on `config.toml`.
- `[filters]` — what counts as a target job. The four regexes compile straight out of the TOML (`role_include`/`role_exclude`/`location_include`/`location_exclude`) plus `max_years_experience`. `*_keywords` lists (word lists) override the raw regex when non-empty; `re.escape` is applied to each word. `location_priority_tiers` (ordered keyword groups) drives the sort and the `Tier` field sent to the UI.
- `[boards]` — per-ATS `enabled` + slug lists (`ashby`/`greenhouse`/`lever`), plus company-level `keep`/`drop` lists matched case-insensitively against the displayed company name (which for ATS boards is the URL slug in Title Case). Non-empty `keep` = allow-list; `drop` always wins.
- `[feeds]` — on/off booleans for the six non-ATS sources; WWR feed slugs, LinkedIn guest query URLs, and Zoho Recruit sites (`"company | site | page_name"` strings) live here too.
- `[run]` — `dedup` (drop overlapping postings: same apply URL, or same source+company+title+location — WWR's category feeds overlap heavily; different locations are separate reqs and survive), `max_workers` (threads), `timeout_seconds`, `web_port` (env `WEB_PORT` overrides), `cache_ttl_seconds`, `snapshot_path` (`data/snapshot.json` — web-mode cache persistence, regenerated data, gitignored), `live_feed_path` (env `LIVE_FEED_PATH` overrides), `preview_count`.
- `[enrich]` — optional Gemini Flash-Lite JD annotation (OFF unless `GEMINI_API_KEY` is in the env AND google-genai is installed; the API key is NEVER in config.toml, which is public). `model`, `max_jobs` (annotation cap per scrape — quota guard), `concurrency` (small pool, flood-proofing), `timeout_seconds`, `max_desc_chars`. ANNOTATION, NEVER GATING: the model only fills advisory `AI_YOE` / `AI_Remote` / `AI_Salary` / `AI_Stack` / `AI_Note` on rows that already passed the deterministic filters — a scrape is reproducible and an API outage can only blank a column, never drop postings. Only NEW rows are annotated: rows whose URL appeared in the previous scrape adopt the old annotation (`AI_Done` marks final annotations), cap-storage via `max_jobs`; rows past the cap stay blank and retry on a later run. YC/LinkedIn rows have no JD text and stay blank. `AI_Done` and `_desc` are internal keys — never in the CSV (extrasaction=ignore) or the snapshot; `_desc` is stripped in `collect_jobs` before anything escapes.

Regexes in TOML must be single-quoted *literal* strings (`'...'`) — double-quoted TOML strings would eat the backslashes (`\b` becomes backspace). A wrong regex or slug fails silently in results; `--verify` is the loud path.

## Gotchas

- **Interpreters:** Python 3.12+ is hard-required — `.python-version` pins the repo to the pyenv virtualenv `job-searcher` (3.12.0) and the config is parsed with stdlib `tomllib`. There is no fallback parser anymore: on older interpreters `import tomllib` fails loudly.
- Target profile: early-career (cap set by `[profile].years_experience`) backend / AI-infrastructure / distributed-systems roles, remote-global first — the exact preferences live in `[profile]` + `[filters]`, which are the canonical source. Resume files stay in the gitignored `work/` directory; do not name real resume versions here.
- The current filters still intentionally drop seniority titles (`senior`, `sr`, `lead`, `staff engineer`, `principal`, `manager`, …) for the ~2 YOE profile — don't remove them from `role_exclude_regex`. The staff branch is `staff(?: \w[\w-]*){0,2} engineer|staff sde|staff swe` — up to two words between "staff" and "engineer" (Staff Product/Data/ML/… Engineer) — NEVER bare `staff`: bare `staff` would kill legitimate mid-level "Member of Technical Staff" titles (Palantir's standard role on Lever).
- All fetches have `except Exception: pass`, so failures are silent. Company/location field shapes differ per ATS: Greenhouse nests location under `location.name`, Lever under `categories.location` with `workplaceType`, Ashby has a separate `isRemote` flag.
- Greenhouse must be fetched with `?content=true` or the description is absent and the YOE filter silently stops applying; Lever descriptions come in the plain `?mode=json` payload. The `/application` apply-link suffix is Ashby-only.
- The strict YOE check only runs where a description exists (HN: full post text; RemoteOK/WWR/Zoho: description; YC/LinkedIn: no descriptions → `Max_Stated_YOE` is `n/a` and the filter can't apply there).
- `EXCLUDE_LOC_REGEX`'s second branch is deliberately boundary-free: `remote\s*[(\[]?\s*-?\s*u\.?\.?\.?\s*[)\]]?` matches "Remote (US)" which ends on `)` — `)` has no trailing `\b`, so a uniformly-boundaried regex would let US-only posts through.
- Non-ATS source quirks: **YC** guest access serves only ONE fixed ~30-job sample (filters/pagination are client-side Inertia, ignored without login; no descriptions). **HN** posts parse as "Company | Role | Location" with a fallback to the opening 150 chars; a window-check drops "Remote" posts naming a US/Canada region unless an allowed region appears in the same window (`_HN_ALLOWED_REGIONS`); posts whose opener is metadata rather than a company name ("Location: X Remote: Yes …", "Position: …") are dropped outright — no Company/Title can be parsed from them. **RemoteOK** returns just the last 100 postings and empty location → "Remote (Global)". **WWR** RSS descriptions rarely state years → YOE usually n/a. **LinkedIn** guest parser 429s constantly without cookies — one request per query, never add per-job detail fetches; company comes from `base-search-card__subtitle`, whole-source zero rows is common. **Zoho Recruit** uses the public endpoint the official `embed_jobs.js` widget calls; site/page_name come from the employer's `rec_embed_js.load(...)` snippet.
- The web UI keeps the applied / not-for-me trackers entirely client-side in `localStorage` under `appliedJobs` and `offRoleJobs`, keyed by `Direct_Apply_URL` (the keys are unchanged from the old checkbox UI, so existing marks survive; the picked category view is also remembered under `jobsView`, default `active`). The toolbar has a segmented Active / ✓ Applied / ✕ Not-for-me / All switcher — **Active is the default view and hides every marked row**, so marking a job ✕ removes it from the dashboard immediately. Rows get ✓-applied (green) and ✕-not-for-me (red) pills; the tracker panel lists both states with dates, exports them to CSV client-side, and has a double-confirmed wipe. Both trackers are per-browser only; URL changes between scrapes orphan a job's marks.
- Fetches run with `ThreadPoolExecutor(max_workers=[run].max_workers)` and `[run].timeout_seconds`, gzip requested in `fetch_json`/`fetch_text` (urllib doesn't decompress itself; Greenhouse `?content=true` boards ship 10–30 MB raw vs ~1 MB gzipped). Lever is slow server-side (10–40 s on big boards like `palantir`) and dominates total scrape time (~1 min); the web mode's background cache hides this. `WEB_PORT` env overrides `[run].web_port`. Scrapes happen strictly on demand — there is no scheduler: a plain page load serves the cache and only kicks a background re-scrape once the TTL expired; the Refresh button forces one immediately via `/jobs?refresh=1` (`refreshing` is reported even on a TTL-fresh cache so the UI's poll can't stop early). When a re-scrape completes it's written with an atomic replace to `[run].snapshot_path`, so a restart serves the last scrape instantly instead of re-scraping for a minute; the one warm-up scrape at startup happens only when there is no usable snapshot. Failures leave the cache memory-only (server-wide `except Exception: pass` philosophy). `/jobs` answers instantly and, alongside `"refreshing": true`, kicks off a background re-scrape (a `running` flag prevents overlapping scrapes; it is set *before* the thread spawn so a fast poll can't observe the gap and stop early); the UI polls every 2.5 s and swaps the fresh data in automatically, so a single Refresh click eventually shows the new scrape without blocking. A run hits ~110 live endpoints, so it needs network access.
- Board slugs are the ATS's URL slug exactly (e.g. `convex-dev` for Convex on Ashby, `grafanalabs` for Grafana) — casing varies per API and wrong slugs fail silently. The curated lists tilt toward seed–Series C startups and get pruned after `--verify` runs. Companies migrate ATSes constantly, which is how slugs go dead.
